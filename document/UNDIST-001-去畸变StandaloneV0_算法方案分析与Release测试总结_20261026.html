3. 去畸变算法方案分析

3.1 算法本质：预计算 4-tap 双线性 LUT 重映射

这套实现不含任何相机内参或畸变模型。它把「去畸变」完全离屏预计算成 12 张与目标图同尺寸的浮点表，运行时只做一次「按表取 4 点 + 加权求和 + 量化」。 所以它是一个定点化的查表重映射（LUT remap with fixed 4-tap bilinear）， 而不是传统意义上的「按畸变公式反解坐标」。

表文件含义实测取值范围
U 坐标U_1..U_4.bin 4 个插值点的源 x 坐标（已被截断为整数） 0 … 5119（trunc() 后存成 float）
V 坐标V_1..V_4.bin 4 个插值点的源 y 坐标（已被截断为整数） 0 … 4095
权重A1..A4.bin 4 个点的双线性权重 各 ∈ [0, 1]，4 者之和 = 1 ± 5.2×10⁻⁸
关键结构事实（本次实测得出，直接决定 GPU 方案的形态）：
  1. U/V 只存整数部分，小数部分完全在 A 里。 例如输出像素 (x=100, y=2000) 处 u=(84,85,84,85)、 v=(2000,2000,2001,2001)、 a=(0.324829, 0.000094, 0.674882, 0.000195)—— 等效采样点是 (84.0003, 2000.675)。 因此 A 无法由 U/V 推出，但它本身是秩 1 的： fu = a₁+a₃、fv = a₂+a₃，再乘出 4 个权重。
  2. 4 个 tap 的几何关系是固定的： tap0=(u₀,v₀)、tap1=(u₀+1,v₀)、tap2=(u₀,v₀+1)、tap3=(u₀+1,v₀+1)。 在 111,596 个抽样有效像素上零违例。 → 4 张索引表可压缩成 1 张基址表 + 3 次 +1 / +W / +W+1。
  3. 位移很小且几乎只沿 x：|Δu| 均值 6.64 px（p99 = 25，max = 30）； |Δv| 均值 4.78 px（p99 = 19，max = 23）； 沿 x 的导数 |du/dx| 均值 1.0089（p99 = 1.0，max = 2）， 沿 y 的导数 |dv/dy| 均值 0.0028（p99 = 0，max = 1）。 → 相邻输出像素读取相邻源地址，访存天然近似合并（coalesced）， 这也是后面 GPU 能跑到 ~86% 带宽上限的原因。

3.4 边界语义：全有或全无

合法条件
4 个插值点必须全部满足 u ≥ 1 且 v ≥ 1 且 u < W 且 v < H。 注意下界是 1 而不是 0，所以第 0 行/第 0 列永远不可能参与插值。
越界处理
只要有一个点越界，4 个索引全部改指向哑像素 N（值为 0）。 权重不清零——所以结果是 0 × Σw = 0，即输出纯黑。
实测比例
350,805 / 20,971,520 = 1.6728% 的像素因此恒为 0（黑边）。 这个数字由 4096×5120 三个独立路径（C++ 库日志、 测试内复刻实现统计、NumPy 参考实现统计）得到，完全一致。
为什么重要
任何 GPU 复刻都必须逐位复现这一语义。它等价于 「把 [N, N+4) 这 4 个位置全部填 0，并让越界像素的索引落进这段零区」， 从而在 kernel 里不需要任何分支或 mask。

3.6 为什么不能用 cv::remap / 纹理采样替代

直觉上「4 点双线性」就是 cv::remap(..., INTER_LINEAR) 或 GPU 纹理采样的 grid_sample。但两者都不能复刻本算法：

替代方案为什么不行量化证据
cv::remap INTER_LINEAR ① 它从 (u,v) 的小数坐标现算权重，而本算法的分数部分只存在 A 里、 U/V 已被截断；
② 它的边界策略是 BORDER_REPLICATE/CONSTANT，不是「全有或全无」；
③ 它按 floor 取左下角，本算法要求 u ≥ 1 的额外排除		 需要重新生成 map1/map2（2×84 MB 浮点），且 4 个特殊语义都得额外 mask
GPU 纹理采样（tex2D bilinear） 硬件插值单元的权重只有 8 bit 小数精度 把 A 权重量化到 1/256 网格后，平均误差 0.991 LSB、最大 1.988 LSB → 会有约 30–50% 的像素差 1–2
torch.nn.functional.grid_sample 同样受硬/软插值精度限制；且 align_corners 与坐标系定义又多一层歧义 同上量级
把权重降到 fp16 fp16 尾数 11 bit，权重误差 ~5×10⁻⁴，累计到 0–255 值域后跨过 .5 边界的概率不可忽略 实测（200 万像素抽样）：6.81% 的像素差 1， 累加值最大绝对误差 0.317
结论：必须自己实现 4-tap gather + fp32 加权 + floor 量化。 好消息是这正好可以用 TensorRT 的原生算子拼出来（GatherMode.ELEMENT）， 不需要写 CUDA kernel；坏消息是这么做就「表带宽受限」（见 UNDIST-002 §7）。

(3) Amdahl：为什么"只有 2.5×"是数学必然

设串行部分（与算法无关、换 GPU 消不掉）= T_io = 22.725 + 1.099 + 15.415 = 39.24 ms， 可加速部分 = T_algo = 63.82 ms。把算法加速到 k 倍后： 

          T_io + T_algo            103.06
  S(k) = ───────────────── = ────────────────────────
          T_io + T_algo / k      39.24 + 63.82 / k

  k = 1     → 1.00×      （现状）
  k = 5     → 1.80×
  k = 12.7  → 2.39×      （GPU pageable 5.017 ms）
  k = 24.9  → 2.53×      （GPU pinned  2.562 ms）   ← 之前说的 2.5×
  k = 69.4  → 2.64×      （GPU kernel-only 0.920 ms）
  k → ∞     → 2.63×  ← Amdahl 天花板：算法归零也只能快 2.6 倍

所以那句「相对现状 103.06 ms 只有 2.5×」的正确理解是：

  • 2.53× 已经是 Amdahl 天花板的 96%（2.53 / 2.63）。 换句话说，再优化算法一分钱都不值——剩下的 2.4 ms 差距全在"算法本身还没到 0"上， 而不是"GPU 不够快"。
  • 瓶颈已经从"算"变成了"搬"：39.24 ms 的非算法开销里， 有 ~32 ms 是把 21 MB 图像在 BMP 编解码器里搬两趟。 在这个形态下，优化 BMP 路径的收益大于优化去畸变算法。
  • 但 103.06 ms 不该被当成部署基线——真实产线上相机给的是内存里的 buffer （甚至直接在显存），输出直接喂给下一个节点， imread/imwrite 根本不存在。 那时正确的基线是 63.82 ms，对应 24.9×（pinned）或 69.4×（图在显存）。

7. 性能瓶颈归因

7.1 主瓶颈：vpgatherdd 的指令吞吐，而不是 DRAM 带宽

证据链是「多线程扩展性」实验。把「gather + quantize」按像素区间切给 N 个线程：

线程数gather+quant 中位相对 1T 加速 相对理论线性判断
142.8631.00×100% 基准
426.6791.61×40% 已明显偏离线性
824.4331.75×22% 接近饱和
1624.0351.78×11% 饱和
20（全部物理核）22.9351.81×9% 硬墙

为什么 20 核只有 1.81×？

若是 DRAM 带宽受限，那 20 线程应能把「有效带宽」从 30.6 GB/s 拉到 ~100 GB/s （DDR5-6400 双通道理论上限 102.4 GB/s），也就是 3× 以上。 实测只有 1.81×，说明瓶颈在核内： vpgatherdd 在 Intel 上是微码实现的，对 32-bit 元素每周期只能算 1 个元素， 一个 _mm256_i32gather_ps（8 元素）约需 8–10 周期。 每像素 4 次 gather → 2097 万 × 4 = 8389 万次元素收集 ≈ 8389 万周期 / 4.3 GHz ≈ 19.5 ms 的理论下界， 实测 gather 阶段 35.63 ms（含 DRAM 等待），单线程 42.86 ms。 多线程并不能绕过「每核每周期 1 元素」这个限制，只能增加并行核数——所以天花板很低。

7.2 21.1% 的时间花在只为日志服务的扫描上

scan_in 10.03 ms + scan_out 3.44 ms = 13.47 ms = 21.1%。 这些数值只被 LOG_DEBUG("CORE", "Input data range: min=%.2f, max=%.2f", ...) 使用， 在 Release 生产路径上毫无意义。这是全项目性价比最高的一处修改：删 4 行代码（或加个宏）省 1/5 时间。

顺便解释一下为什么 scan_in（10.03 ms）是 scan_out（3.44 ms）的近 3 倍： 前者扫 84 MiB 的 float（两趟 = 168 MiB），后者扫 20 MiB 的 uint8（两趟 = 40 MiB）， 比值 4.2× ≈ 时间比 2.9×（后者受更小的数据结构缓存友好度影响）。

7.3 quantize 的实现方式浪费了约 3–4×

convertFloatToByteAVX2() 把 8 个结果 _mm256_storeu_si256 到栈上 int lanes[8]，再逐字节写 output[i]…output[i+7]。 这等于把已经向量化的结果又拆成 8 次标量存储，且栈上的中转会被 L1 反复读写。 

// 现状（Undistortion.cpp:1095-1107）—— 8 次标量字节存储
__m256i vi = _mm256_cvttps_epi32(vf);
int lanes[8];
_mm256_storeu_si256((__m256i*)lanes, vi);
output[i+0] = (uint8_t)lanes[0]; ... output[i+7] = (uint8_t)lanes[7];

// 建议：packs 两轮 + 一次 8 字节存储（约 3-4× 提速）
__m128i lo = _mm256_castsi256_si128(vi), hi = _mm256_extracti128_si256(vi, 1);
__m128i p16 = _mm_packs_epi32(lo, hi);              // 8×int32 → 8×int16
__m128i p8  = _mm_packus_epi16(p16, p16);           // → 8×uint8 在低 8 字节
_mm_storel_epi64((__m128i*)(output + i), p8);

按 7.46 ms 降到 ~2 ms 估算，可再省 5.5 ms（8.5%）。

7.4 cvt_in 也有 3–4× 余量

std::copy(uint8_t*, uint8_t*+N, float*) 是 21 MB 读 + 84 MB 写 = 105 MB， 实测 5.26 ms → 19.9 GB/s。若用 AVX2 一次把 8 个 uint8 转成 8 个 float（_mm256_cvtepu8_epi32 + _mm256_cvtepi32_ps）， 在 20 GB/s 的 DRAM 下界之上还能再压到 ~3 ms。 更好的做法是彻底去掉这一趟——见 §8 的「u8 直接 gather」。

7.5 侧数据规模就是天花板

算法每处理 1 个像素，必须读 4 个 int32 索引（16 B）+ 4 个 float 权重（16 B）= 32 B， 再加上输入 4 B × 4 与输出 1 B。也就是说每像素 ~50 B 的访存需求、与图像内容无关。 对 20.97 MPix 就是 ~1.05 GB/帧。 单线程 63.8 ms → 16.5 GB/s；多线程天花板 1.81× → 30 GB/s。 这就是为什么 CPU 侧无论如何优化都只能到 30–45 ms 量级， 而 GPU 的 298 GB/s 有效带宽能把它压到 1 ms 级（见 UNDIST-002）。

9. 结论与后续

  1. 算法已彻底梳理清楚：预计算 4-tap 双线性 LUT 重映射， 语义包括「U/V 只存整数、权重全在 A、tap 几何固定为 2×2、 越界全有或全无、clamp→+0.5→trunc、FMA 链」六个要点， 已用复刻实现（0 差异 / 838.86 MPix）与 NumPy 独立实现（6.03×10⁻⁶）双向锁定。
  2. 流程已跑通且产物可信：40 张 5120×4096 → demo/output0， 几何正确、锐度正常、黑边比例 1.6728% 与语义一致。
  3. Release 性能基线：infer 63.82 ms（中位 64.63，p90 66.68，σ 3.05）， 端到端 103.06 ms，324.5 MPix/s / 15.5 fps。 端到端里 38.1%（39.24 ms）与算法无关，其中 ~32 ms 是 BMP 编解码纯搬运 —— 这是"用磁盘 BMP 模拟相机"的脚手架代价，不是产线基线（见 §6.2.1）。
  4. CPU 侧的三个确定收益点：去掉调试扫描（−21.1%）、 quantize 向量化（−8.5%）、融合 gather+quant（−4 ms）， 合计可到 ~41 ms 单线程 / ~23 ms 多线程。
  5. CPU 没有数量级空间：vpgatherdd 每周期 1 元素的硬限制， 20 核只有 1.81× 加速。要 1 ms 量级必须走 GPU。
  6. 加速比取决于"要不要搬图"，不取决于 kernel：同一条 0.92 ms 的 GPU kernel， 放进"读 BMP→算→写 BMP"的链路只值 2.5×（Amdahl 天花板 2.63×）； 放在"内存直传"值 24.9×；放在"图像不出显存"值 69.4×。 落地第一步应是挪动节点位置，而不是调 kernel。
  7. 工程债已清一项（见 §2.4）：CPPAPP/ 已整目录删除 （27 文件 / 274 KB），唯一有价值的 Undistortion_raw.cpp 归档到 reference/；重建 3 目标成功、回归 0 差异。 其余未处理：陈旧路径配置、980 MiB 死内存、noexcept 里 throw、 __FMA__ 强制定义导致运行时检测被绕过、C# 每帧 2 次 21 MB 托管拷贝。
