1. 结论摘要

可映射性
整套算法可只用 TensorRT 原生算子表达，不需要自定义 plugin、不需要 CUDA kernel： Cast + Shuffle + Concatenation + 4×Gather(GatherMode::ELEMENT) + ElementWise + Activation(CLIP) + Unary(FLOOR) + Cast。共 20 个层。
实测性能
RTX 5060 Laptop 上 p50 = 0.9765 ms / 图（b=1，fp32，100 次迭代均值 1.0380 ms）， 21,476 MPix/s。相对 CPU 的 63.82 ms 是 65.4×。
结果一致性（双域逐位置审计）
① 浮点域（量化前）：62,914,560 个位置中，|Δ| > 0.001 灰度的位置数 = 0。 最大 |Δ| 仅 6.104×10⁻⁵ 灰度（比阈值小 16.4 倍）， 连 >10⁻⁴ 的位置也是 0 个 —— 严格满足「每个位置差异 < 0.001 灰度」。
② 灰度域（uint8 输出）：差 1 的像素 383 / 62,914,560 = 6.088×10⁻⁶， 最大差 1（差 ≥2 的：0 个），等效 MAE = 6.088×10⁻⁶ 灰度、 PSNR ≈ 100 dB。
差异 100% 来自 GPU 把 mul+add 融成 FMA 的末位舍入 —— 与 CPU 自身 「FMA 链 vs mul+add」的差值（5.44×10⁻⁶）完全同量级， 即 TRT 没有引入任何 CPU 侧不存在的不确定性。
关键优化发现
侧数据（表）从 32 B/px（671 MB） 压到 12 B/px（252 MB） 后， 单图从 2.108 ms → 0.9765 ms（2.16×）。 原因：这个 kernel 是表带宽受限——252 MB 的表在 298 GB/s 下要 0.845 ms， 已占实测时间的 86.5%。进一步优化的唯一杠杆是继续缩小表。
端到端的真实瓶颈是 PCIe
同口径整合实测（主机内存 → 接口 → 主机内存，60 次）： pageable 5.017 ms → pinned 2.562 ms → kernel-only 0.920 ms。 即「每帧走一次 PCIe」时，传输（1.64 ms @pinned / 4.10 ms @pageable）是 kernel 的 1.8～4.5 倍，净收益只剩 24.9×（pinned）/12.7×（pageable）。 把主机缓冲换成页锁内存是最便宜的一项改动（12.7× → 24.9×）；多流流水化实测只多 2.6%， 不要指望它。要做到 ~1 ms/图 必须让图像在显存内产生并消费（相机直采 / 前序 GPU 节点）。
批量的正确做法
用原生算子做 batch 会把索引广播成 [B, N] int32（B=8 时 672 MB 中间量）， 反而更慢。要摊薄表带宽必须写一个 TRT plugin/CUDA kernel，让 252 MB 的表只读一次服务整批： B=8 预估 1.972 ms/批 = 0.247 ms/图（推算，模型已在 B=1 上被实测验证，误差 1%）。
一句话方案：离线把 12 个 .bin 压成 3 张紧凑表 （idx0 int32 + fu/fv fp32，共 252 MB，尺寸与目标图一致）， 运行时用一条 20 层的 fp32 强类型 TRT 网络做「4-tap gather + 权重重建 + FMA + clamp + floor」， 外面套一层与 INFER/deploy 完全同构的 8 导出 C ABI + C# IDisposable 封装。

(2) 为什么"只差 383 个像素、每个差 1" 而不是"系统性偏差"

量化规则是 trunc(clamp(v,0,255) + 0.5)。设真值 v 与 GPU 结果 v+δ， |δ| ≤ 6.1×10⁻⁵。只有当 v 落在某个 .5 边界两侧 ±δ 的窄窗内 （窗宽 = 2δ ≈ 1.2×10⁻⁴，占整个 1.0 灰度步长的 1.2×10⁻⁴）才会翻转， 所以翻转概率的上界就是 2|δ|/1.0 ≈ 1.2×10⁻⁴。

实测翻转率 6.088×10⁻⁶，比这个上界还低 20 倍 （因为图像灰度值并不均匀落在 .5 附近，而是连续分布）。 这说明 383 个差 1 的像素完全是真实值恰好处在舍入边界造成的"硬币翻转"， 不是任何位置上的系统性偏移 —— 这也解释了为什么没有任何一个像素差 ≥2。

(3) 关键判据：TRT 的偏差没有超出 CPU 自身的浮点不确定性

//   over_thr              = 0            ✔
//   max_abs_uint8_diff    = 1            ✔
//   diff_ratio            = 6.088e-06    ✔ (阈值 1e-05，余量 1.6×)
//   mae_gray              = 6.088e-06    ✔ (阈值 1e-03，余量 164×)

为什么"位级完全相等"不可作为验收条件： CPU 自己都做不到 —— 同一份代码只把 _mm256_fmadd_ps 换成 _mm256_mul_ps + _mm256_add_ps，就有 114 个像素从 0 变成差 1。 这是 IEEE-754 结合律的性质，不是实现质量问题。 若业务确实要求位级相等（0 个像素差），只有两条路：

  1. 统一算术形式：CPU 与 GPU 两侧都用"显式非融合"写法 （GPU 用 __fmul_rn/__fadd_rn 的 CUDA kernel，CPU 去掉 fmadd）， 则可做到逐位相等。代价：要写 CUDA kernel（放弃"纯原生算子"）， 且 CPU 侧现有产物会变（需重新确认基线）。
  2. 放弃 GPU，用 CPU 多线程（~23 ms）。但那样就回到 2.8× 而不是 25×。

我的建议：采用上面的四行断言（浮点域 0 个位置超 0.001 + 灰度域最大差 1 + 比率 ≤1e-5）， 而不是位级相等。 它既严格覆盖了"每个位置差异 < 0.001 灰度"这一要求， 又不与浮点运算的物理性质对抗。

4.2 边界语义的零分支复刻

要复刻的语义（来自 UNDIST-001 §3.4）： 4 个 tap 必须全部满足 u≥1, v≥1, u<W, v<H，否则整像素输出 0（1.6728%）。

复刻手法：把「越界」变成「索引指向零区」。

  1. Host 侧构造 idx0 时，若 4 个 tap 有任一越界，就让 idx0 = N（哨兵）。
  2. 网络里把输入展平后再拼接 5124 个 0，得到长度 N + 5124 的查找表。
  3. 4 个 tap 的索引分别是 idx0, idx0+1, idx0+W, idx0+W+1。 idx0 = N 时派生索引最大到 N + W + 1 = N + 5121， 全部落在 [N, N+5124) 的零区。4 次 gather 全部读到 0。
  4. 结果 0×w0 + 0×w1 + 0×w2 + 0×w3 = 0，与 CPU 的「权重不清零 × 哑像素 0」完全一致。

收益：kernel 里没有任何分支、没有 mask、没有 select 层。 如果用 Where(idx < N, gathered, 0) 的方式，会多出 4 个 Select 层 + 4 个比较， 并且需要额外的 4 次全量遍历。

踩坑记录（本次实际遇到的）：若只补 1 个 0（像 C++ 里那样 inputF_[N] = 0）， 变体 E/F 的 idx0+1 和 idx0+W 会越界读到未定义显存， 可能得到 NaN（然后被 clamp 成 0，看起来"对"，但不稳定）或直接 crash。 PAD 必须 ≥ W+2，取 W+4=5124 是为了按 4 对齐、便于常量层生成。

这是本次分析最重要的工程结论：
「69.4×」只在图已经在显存里时成立。
一旦每帧都要走一次 PCIe（21 MB 进 + 21 MB 出）， 传输（1.64 ms @pinned / 4.10 ms @pageable）就是 kernel（0.92 ms）的 1.8～4.5 倍， 单图的净收益只剩 24.9×（pinned） 或 12.7×（pageable）。

所以部署形态的选择比 kernel 优化重要得多：
  • 首选：让去畸变节点在相机采集之后、检测之前，图像始终驻留显存 （GPU 直采 / 前序 GPU 节点），此时按 S0/S3 计，0.25–1.0 ms/图（69～258×）。
  • 次选：必须过 PCIe 时，先把主机缓冲换成页锁内存（12.7× → 24.9×，一行改动）， 再把表与引擎常驻；多流流水收益有限（+2.6%），放到 P2。
  • 不要：在 CPU 侧做 BMP 编解码后再走 GPU —— 那会把 22.8 + 15.4 ms 的 I/O 又加回来 （此时 e2e = 22.8 + 2.56 + 15.4 = 40.8 ms，相对 CPU 现状 103.06 ms 只有 2.5×， 这解释了为什么「加了个 GPU 却感觉没快多少」）。

6.4 为什么「用原生算子做 batch」是反例

TRT 的 GatherMode::ELEMENT 要求 indices 与 data 除 gather 轴外各维一致。要做到 b=8 共享一张 [1, N] 索引表，必须把索引广播成 [8, N]。TRT 没有「免费广播」的 gather，只能用 idx0 + zeros([B,1]) 的 ElementWise 广播去物化，于是产生：

物化 idx0 到 [8, N] int32672 MB 写 + 84 MB 读
物化 idx1/2/3（各 [8, N]）3 × 756 MB
额外流量≈ 3.0 GB
按 298 GB/s 折算+10.1 ms（相对 1.97 ms 的 5 倍！）

结论：批量必须走自定义 kernel / TRT plugin。 在 plugin 里，一个 block 处理一批像素、索引与权重只从全局内存读一次并放 shared memory， 即可实现 §6.2 的摊销。plugin 的实现难度不高（无状态、无动态 shape、单一 dtype）， 是本次方案里唯一值得写 CUDA 的地方。

关于「表能不能更小」的边界： 变体 F 的 12 B/px 已是「必须保留 fp32 权重精度」前提下的近最优解。 再往下压的唯一合法途径是降低坐标索引的位宽（int32 → int8 的 Δ，10 B/px） 或换数据结构（分离压缩流、行内 run-length）。 后者对「du/dx ≈ 1」这种高度规则的字段理论上能压到 1–2 B/px， 但会让 kernel 从「顺序读表」退化为「不规则解码」，很可能反而变慢（GPU 不擅长变长解码）。 建议在 P2 阶段用 profile 数据做决策，不要一开始就上。

// ---------- ImageUndistorter.cs（结构与 RealEsrganUpscaler 完全同构）----------
public sealed class ImageUndistorter : IDisposable
{
    private IntPtr _ctx;
    private bool _disposed;

    public UndistortInfo   Info       { get; }
    public UndistortTiming LastTiming { private set; }

    public ImageUndistorter(string yamlConfigPath)
    {
        if (!File.Exists(yamlConfigPath)) throw new FileNotFoundException(...);

        var code = NativeMethods.undist_init_from_yaml(yamlConfigPath, out _ctx);
        if (code != UndistortErrorCode.Ok)
        {
            // native 在错误路径也会回写句柄：先取消息、再释放、再抛（否则泄漏显存）
            string? msg = _ctx != IntPtr.Zero ? ReadError() : null;
            if (_ctx != IntPtr.Zero) { NativeMethods.undist_release(_ctx); _ctx = IntPtr.Zero; }
            throw new UndistortException(code, msg);
        }
        Info = QueryInfo();
    }

    /// gray: 连续内存、长度 ≥ w*h、无行尾填充
    public UndistortedImage Process(byte[] gray, int w, int h)
    {
        ThrowIfDisposed();
        var handle = GCHandle.Alloc(gray, GCHandleType.Pinned);   // 每帧一次 Pin，不拷贝
        try { return ProcessInternal(handle.AddrOfPinnedObject(), w, h, w); }
        finally { handle.Free(); }
    }

    /// Bitmap 输入：LockBits 取 Scan0，零拷贝
    public UndistortedImage Process(Bitmap bmp)
        => ImageInterop.WithLockedGray(bmp, (ptr, w, h, stride) => ProcessInternal(ptr, w, h, stride));

    private UndistortedImage ProcessInternal(IntPtr src, int w, int h, int stride)
    {
        var sw = Stopwatch.StartNew();
        var code = NativeMethods.undist_process(_ctx, src, w, h, stride,
                                out var raw, out var nativeTiming);
        ThrowIfError(code);
        try
        {
            // 几何契约自检：输出必须与输入同尺寸
            if (raw.width != w || raw.height != h) throw new UndistortException(...);

            int len = raw.stride > 0 ? raw.stride * raw.height : raw.width * raw.height;
            var gray = new byte[len];

            var swCopy = Stopwatch.StartNew();
            Marshal.Copy(raw.data, gray, 0, len);
            double copyMs = swCopy.Elapsed.TotalMilliseconds;

            LastTiming = new UndistortTiming {
                H2DMs = nativeTiming.h2d_ms, InferMs = nativeTiming.infer_ms,
                D2HMs = nativeTiming.d2h_ms, NativeTotalMs = nativeTiming.total_ms,
                CopyMs = copyMs, TotalMs = sw.Elapsed.TotalMilliseconds,
            };
            return new UndistortedImage(gray, raw.width, raw.height, raw.stride);
        }
        finally { NativeMethods.undist_free_image(_ctx, ref raw); }  // 两段式：复制完立即归还
    }

    public void Dispose() { ... NativeMethods.undist_release(_ctx); _ctx = IntPtr.Zero; GC.SuppressFinalize(this); }
    ~ImageUndistorter() { if (!_disposed && _ctx != IntPtr.Zero) NativeMethods.undist_release(_ctx); }
}
