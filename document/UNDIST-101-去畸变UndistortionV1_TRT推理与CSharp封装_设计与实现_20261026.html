1. 结论摘要

算法可映射性
整套去畸变只用 TensorRT 原生算子表达（Cast / Shuffle / Concatenation / Gather / ElementWise / Activation(CLIP) / Unary(FLOOR) / Cast），不需要自定义 plugin 或 CUDA kernel。
交付形态
一个 undist_api.dll（10 个 C 导出）+ 一个 UndistortionV1Inference .NET 8 类库 + Sample/SelfTest；初始化只传矩阵目录与尺寸，推理内存进、内存出，不落盘。
结果一致性
40 张 5120×4096 实测：差异 4,914 / 838,860,800 = 5.86×10⁻⁶，最大 ±1 LSB， 差 ≥2 的像素 0 个，PSNR 最低 99.47 dB。差异 100% 来自 GPU 的 FMA 末位舍入。
性能
kernel 1.198 ms；调用方页锁缓冲零拷贝 2.892 ms/图（345 图/s，22.1× CPU）； 库内 pinned 暂存 4.944 ms；pageable 直传 5.904 ms；CPU Release 基准 63.82 ms。
初始化
12 个 .bin（1 GB）→ 12 B/px 紧凑表 + 引擎加载：2.23 s （表 2.08 s + 引擎缓存 0.15 s）；冷启动构建引擎另加约 3.6 s。
显存
表 251.7 MB + 输入/输出 41.9 MB = 293.6 MB（280 MiB）/实例。
最重要的工程结论
「pinned 比 pageable 快」只在缓冲本身常驻页锁时成立：库内临时 staging 只快 1.19×； 真正的零拷贝路径快 2.04×。托管侧 GCHandle(Pinned)/POH 不是页锁内存，必须补 cudaHostRegister（实测 5.93 → 2.76 ms）。
一句话方案：离线把 12 张 float 矩阵压成 3 张紧凑表（idx0 int32 + fu/fv fp32，共 12 B/px），运行时用一条 32 层 fp32 强类型 TRT 网络做「4-tap gather + 权重重建 + FMA + clamp + floor」，外面套一层与 INFER/deploy 同构的 C ABI 与 C# IDisposable 封装。

3. 参考基线与继承的工程约定

3.1 GOLDENLINE 的检测/分割调用逻辑

GOLDENLINE1.0\2605CDEPLOY\deploy\GoldenWire.Core\Inference 下有两条关键文件： TrtApi.cs 是纯 P/Invoke 绑定，TrtModelRuntime.cs 负责引擎落盘、参数装配、 句柄缓存与批量缓冲。其调用逻辑可以归纳为五步：

// 1) 原生库就绪：应用目录 → runtimes\trt → thirdpart\trt 依次探测 EnsureNative() // 2) 引擎字节落盘 + 生成 C-API 需要的配置（TRT 需要文件路径） PrepareEngine(id) → yaml // 3) 按模型 id 缓存原生句柄：同一引擎多 FOV 共享一个 ctx GetOrCreate(id) → yolo26det_init_from_yaml / unetv2_init_from_yaml // 4) 托管缓冲 pin 住 → 调 C-API → 拷贝回托管数组（每次调用一次边界） pin(bytes) → yolo26det_detect_batch(...) → Marshal.Copy // 5) 失败不静默回退：get_error(ctx) 取串，抛可操作异常 if (code != 0) throw ... get_error(ctx)

对本工程直接可复用的三点：

  • 薄绑定：P/Invoke 层不做业务判断、不缓存状态；句柄与生命周期由上层类管理。
  • 错误即字符串：所有失败路径都保证 get_error(ctx) 可读，且初始化失败也回写句柄， 便于「先取错误、再 release」。
  • 失败不静默降级：引擎/驱动不匹配时明确报错，不偷偷换 CPU 路径。

3.2 INFER/deploy 的 TRT + C-API + C# 分层

INFER\deploy\trt 是插件化框架：plugins/<algo> 放算法实现， src/*_api.cpp 是每个算法的 C-API 薄壳，include/*_api.h 是唯一对外契约； csharp/<algo> 一一对应一个类库 + Sample + SelfTest。 以 realesrgan_api.h 为例，它确立了本工程照搬的形态：

  • 一个算法 = 一个 DLL = 一组 extern "C" 导出，不跨边界传 C++ 类型/STL；
  • 错误码枚举 + get_error 字符串；
  • Info / Timing 结构体回传运行期参数与分段耗时；
  • 两段式释放（库分配的输出由 free_image 归还）；
  • C# 侧：NativeMethods（internal）+ Info/Timing/Exception + IDisposable 封装 + 终结器兜底。

4. 算法 → TensorRT 的映射

4.1 CPU 语义的精确形式

CPU 版本（CAPP/src/Undistortion.cpp）在 setConfig 阶段把 12 张矩阵预计算成 「每像素 4 个源索引 + 4 个权重」，推理阶段只做加权求和与量化： 

u_k = trunc(U_k), v_k = trunc(V_k)          k = 0..3（双线性 4 抽头）
valid = ∀k (u_k ≥ 1 ∧ u_k < W ∧ v_k ≥ 1 ∧ v_k < H)
idx_k = valid ? v_k · W + u_k : N           N = W·H，越界指向值为 0 的哑元
fu = A2 + A4,  fv = A3 + A4
w0 = (1−fu)(1−fv), w1 = fu(1−fv), w2 = (1−fu)fv, w3 = fu·fv
out = uint8( clamp(Σ_k src[idx_k]·w_k, 0, 255) + 0.5 )   先 clamp 后 +0.5，再截断

注意两个容易被忽略的细节，它们决定了 GPU 能否复刻：

  1. 越界是「全有或全无」：4 个抽头只要有一个越界，整个像素输出 0，而不是逐抽头裁剪。 实现上把 4 个索引都指向平坦数组末尾的 0，不需要分支。
  2. 量化是 clamp → +0.5 → trunc，等价于 floor(clamp(x)+0.5)（x ∈ [0,255] 时）。 TRT 侧用 CLIP + Add(0.5) + FLOOR + Cast(uint8) 逐位对齐。

4.2 紧凑表：从 32 B/px 到 12 B/px

该 kernel 的瓶颈是「读表」而不是算力。早期原型比较过三种表结构（详见 UNDIST-002 §5）：

变体表内容B/px表大小 kernel 实测结论
A4×int32 索引 + 4×fp32 权重32640 MiB 2.108 ms最直观，最慢
E1×int32 基址 + 3 次 +1/+W 派生 + 4×fp32 权重20400 MiB 1.349 ms少 3 张索引表
F（本工程）1×int32 基址 + fu/fv 两张 fp32，权重由乘积重建12 240 MiB0.977 ms带宽最小，选中

上表 kernel 数值来自 UNDIST-002 的原型（RTX 5060 Laptop，fp32，b=1，100 次）；本工程 实测 1.198 ms，差异来自驱动/时钟与测量口径，量级一致。

变体 F 的关键假设是「双线性权重可由两个因子重建」，这已由 weight_recon.json 审计：重建权重与 A1..A4 的最大绝对误差 1.19×10⁻⁷，抽头几何关系零违例。因此 4 个权重不必存表，只存 fu、fv。

4.3 网络结构（32 层，无插件）

#层参数输出形状
1Castimg: uint8 → float32[1,1,H,W]
2Shufflereshape[1,N]
3ConstantPAD = W+4 个 0[1,PAD]
4Concatenationaxis=1[1,N+PAD] 平坦图
5–6Constantint32 1 / int32 W[1,1]
7–9ElementWise SUMidx0+1, idx0+W, (idx0+1)+W[1,N] ×3
10–13Gather (ELEMENT)4 个抽头索引在平坦图上取数[1,N] ×4
14Constant1.0f[1,1]
15–16ElementWise SUB1−fu, 1−fv[1,N] ×2
17–20ElementWise PRODw0..w3[1,N] ×4
21–24ElementWise PRODg_k · w_k[1,N] ×4
25–27ElementWise SUM累加 4 项[1,N]
28Activation CLIPα=0, β=255[1,N]
29–30Constant + SUM+0.5[1,N]
31Unary FLOOR—[1,N]
32Castfloat32 → uint8[1,N] → out_u8

4 个网络输入：img uint8 [1,1,H,W]、idx0 int32 [1,N]、 fu/fv fp32 [1,N]；1 个输出 out_u8 uint8 [1,N]（内存即连续 N 字节，等价于 H×W 单通道图）。强类型网络（kSTRONGLY_TYPED） 保证不做隐式 fp16/量化，精度固定 fp32。

为什么能只存 1 张索引表

双线性的 4 个抽头在平坦数组上恰好是 i, i+1, i+W, i+W+1（行主序）。合法性条件 u_k ≥ 1 ∧ u_k < W 与 v_k ≥ 1 ∧ v_k < H 保证了 i+W+1 不会跨行越界；越界像素的 idx0 已被置为 N。平坦输入尾部补 W+4 个 0，使 N..N+W+3 全部读到 0，于是「任一抽头越界 → 输出 0」在 GPU 上变成 零分支的 4 次 gather。

4.4 边界与数值语义的复刻

语义CPUTRT一致性
越界判定4 抽头全部在 [1,W)×[1,H)同一条件离线算进 idx0 逐位
越界输出读哑元 0 → 加权和 04 次 gather 都读平坦尾部 0 逐位
索引取整static_cast<int>（trunc）离线同式 逐位
权重A1..A4 查表fu/fv 重建（误差 1.19e-7） ±1e-7
累加mul+add（或 CPU 自身 FMA 链）FMA 融合 末位舍入
量化clamp → +0.5 → truncCLIP → +0.5 → FLOOR → Cast 逐位

因此最终差异只可能来自「权重重建的 1e-7 扰动」与「FMA 末位舍入」；实测最大 1 LSB、 差异比例 5.86×10⁻⁶，与 CPU 自身「FMA 链 vs mul+add」的 5.44×10⁻⁶ 同量级， 说明 TRT 没有引入 CPU 侧不存在的不确定性。

5.2 数据流与生命周期

初始化（一次，~2.2 s） matrix_dir ──► build_tables ──► idx0[84MB] fu[84MB] fv[84MB] │ ├─ cudaMalloc + H2D（252 MB，~27 ms）→ 显存常驻 └─ build/load engine（37 KB）→ context 推理（每帧） src(pageable/pinned) ──► [H2D] ──► 平坦图 + 4 gather + FMA ──► [D2H] ──► dst │ │ └── 4 张表只读，不在每帧重传

表与引擎都是「初始化一次、常驻显存」，每帧只有 21 MB 进 + 21 MB 出。用 undist_info 可以把 table_bytes、device_bytes、 init_*_ms 回传给上层做资源核算与启动耗时上报。

5.3 并发与线程模型

  • 一实例一条 stream、一个 context；undist_process 内部加互斥锁，多线程不会崩但串行。
  • 要去并行：每线程一个实例。每实例 280 MiB 显存，8 GiB 卡按显存算可开 20+，工程建议 ≤16 留余量。
  • 所有导出函数都 try/catch 兜底，异常不会穿过 C ABI；失败统一写 ctx->error。
  • 析构顺序：先释放 CUDA（pinned/device/stream），再销毁 TRT 对象，避免 context 已销毁后释放显存。

表 / 引擎 / 显存库随 ctx 释放常驻，不在每帧重建

pinned 暂存库（cudaHostAlloc）随 ctx / 切模式2×21 MB
调用方 pinned调用方调用方（host_unregister）须页对齐；配合 host_flags=1
host_flags 的含义：bit0=1 表示 「src/dst 已经是页锁内存」，库会跳过内部暂存直接异步 DMA。 如果调用方传了 host_flags=1 但缓冲其实是普通 pageable 内存，结果仍然正确 （CUDA 会自动退回同步语义），只是会变慢且失去异步性。

7.2 三种入口：Mat / byte[] / PinnedBuffer

// 1) 最常用：Mat 进 Mat 出（库内 pinned 暂存，pageable 兼容）
using var und = new Undistorter(matrixDir, 5120, 4096);
using var src = Cv2.ImRead(path, ImreadModes.Grayscale);
using var dst = new Mat(4096, 5120, MatType.CV_8UC1);   // 复用，避免每帧 21MB 分配
und.Process(src, dst);
Console.WriteLine(und.LastTiming);   // h2d=0.78 infer=1.17 d2h=0.78 total=4.94 ms

// 2) byte[]：适合与相机 SDK / 网络包对接（每次 pin 数组，有开销）
byte[] outBytes = und.Process(inBytes);

// 3) 零拷贝：PinnedBuffer 复用，host_flags=1，直接异步 DMA
using var pinIn  = new PinnedBuffer(5120 * 4096);
using var pinOut = new PinnedBuffer(5120 * 4096);
pinIn.CopyFrom(src.Data, pinIn.Length);
und.ProcessPinned(pinIn, pinOut);
pinOut.CopyTo(dst.Data, pinOut.Length);

Mat 入口会检查 CV_8UC1、尺寸、连续性；不连续时自动 Clone（并计一次拷贝）。 dst 为 null 时新建 Mat，但高频路径建议复用，否则每帧 21 MB 托管分配会拖慢 GC。

7.3 关键坑：POH ≠ 页锁内存

实测踩坑：第一版 PinnedBuffer 用 GC.AllocateArray<byte>(n, pinned: true) + GCHandle(Pinned)， 以为就是 CUDA 的 pinned memory。结果零拷贝路径实测 5.93 ms，和 pageable 几乎一样。 原因：GCHandle(Pinned) 只保证「GC 不移动该对象」，不是操作系统的非分页内存； CUDA 仍按 pageable 处理并内部暂存。

修正：PinnedBuffer 在构造时调用 undist_host_register （即 cudaHostRegister）把这段 POH 内存真正页锁，Dispose 时 cudaHostUnregister。同一份代码立刻从 5.93 ms → 2.76 ms（2.15×）。 这条经验对任何「C# + CUDA」封装都成立。

8. 主机内存搬运：pageable vs pinned

8.1 机制差异

pageable（可分页）

  • 普通 malloc/new / 托管数组，操作系统可换出、可移动。
  • CUDA 不能直接 DMA：驱动在内部准备一块页锁中转缓冲（bounce buffer）， 先 CPU→中转、再 DMA；D2H 反向再拷一次。
  • cudaMemcpy 对 pageable 是同步语义；cudaMemcpyAsync 也可能被驱动 降级为同步。
  • 额外一次内存拷贝 + 驱动锁，带宽打对折，尾延迟抖动大。

pinned（页锁）

  • cudaHostAlloc 或 cudaHostRegister 分配/注册，物理页常驻、不可换出。
  • GPU 的 DMA 引擎直接读写主机物理地址，无中转拷贝。
  • cudaMemcpyAsync 真正异步，可与 kernel/其它流重叠。
  • 代价：占用不可换出的物理内存；过量分配会拖慢整机；分配/注册是毫秒级操作， 必须复用而不是每帧做。

三个必须解释的现象

  1. pageable 的 D2H（2.698 ms）比 H2D（1.913 ms）更贵。 回读时驱动必须等 DMA 完成并把数据从中转缓冲拷回用户页，WDDM 下还要处理分页/驻留； 实测 p90 达 5.6 ms，尾延迟明显。
  2. 库内 pinned 暂存只比 pageable 快 1.19×（4.944 vs 5.904）。 因为「pageable→pinned」的 2×1 ms 主机 memcpy，成本几乎等于驱动自己做的中转。 换句话说：如果数据本来就在普通内存里，换 pinned 只是把中转从驱动搬到了你的代码里。
  3. 真正的收益来自「缓冲常驻页锁」：2.892 ms，是 pageable 的 2.04×。 这时每帧只剩 0.77 + 1.35 + 0.77，PCIe 传输占 53%，kernel 占 47%。

推荐值的含义：本工程推荐「调用方常驻 pinned + 零拷贝」作为单图部署的目标值 2.9 ms/图；若上游只能给普通 Mat，则按 4.9 ms/图 计价，不要按 kernel 的 1.2 ms 报指标。 pinned 缓冲要在初始化时分配、循环复用；每帧 cudaHostRegister 会把收益吃光。

什么时候不要用 pinned

  • 图像只处理一次、之后马上释放：注册/注销的成本高于收益。
  • 多实例/多相机且主机内存紧张：每路 2×21 MB 页锁内存不可换出，累积会拖慢整机。
  • 需要与其它进程共享大页/内存池：页锁内存与内存池策略可能冲突，需单独评估。

9. 实现细节

9.1 紧凑表构建

  1. 文件校验：12 个 .bin 必须存在且大小 = W·H·4；不符返回 -6/-7， 错误串带文件名与实际大小。
  2. 列主序 → 行主序：源文件是 raw[col·H + row]，用 32×32 分块转置， 避免整列跨距写导致的缓存抖动。
  3. 流式掩码：不一次性保留 8 张 U/V（672 MB），而是逐张加载、更新 uint8 掩码后释放； 峰值主机内存约 350–450 MB，而不是 1.3 GB。
  4. 索引：用 U1/V1 算 v·W+u，四抽头任一越界则置 N；N = 20,971,520， 在 int32 范围内（上限留 16 个哑元）。
  5. 权重因子：fu = A2+A4、fv = A3+A4，只保留两张表； 实测 valid = 20,620,715，越界 = 350,805（1.6728%），与 V0 的审计值一致。

本机实测：读 1 GB + 转置/掩码/权重 ≈ 2.08 s。属于一次性启动成本；若要压到 <500 ms， 可把表做成离线产物（直接发布 idx0/fu/fv 三张 .bin），运行时只做 H2D。

9.2 引擎构建与缓存

  • 强类型网络（kSTRONGLY_TYPED），workspace 256 MB，无 tactic 搜索需求（全是逐元素/gather）。
  • 冷构建 3.6 s（首次），序列化后仅 37.1 KB；再次启动反序列化 ~150 ms。
  • 缓存文件 = 32 字节头 + 引擎字节： magic "UDV1" / version / W / H / variant / TRT 版本 / table_bytes。 头不匹配（尺寸、表结构、TRT 版本）自动回退重建，避免「换了矩阵却加载旧引擎」。
  • 缓存是可选能力，默认关闭；图像数据从不落盘，符合「数据都放内存」的要求。

9.3 推理路径与计时点

total = t0 ─────────────────────────────────────────────── t5
  ├─ 主机行拷贝（仅 staging 路径）        t0..t1
  ├─ H2D（async + streamSync）             t1..t2
  ├─ enqueueV3 + streamSync（kernel）    t2..t3
  ├─ D2H（async + streamSync）             t3..t4
  └─ 主机行拷贝回 dst（仅 staging 路径）  t4..t5
  • 串行口径：每段结束都 cudaStreamSynchronize，所以 h2d/infer/d2h 可加， 与 total 的差额就是主机拷贝时间，便于定位瓶颈。
  • pageable 模式用同步 cudaMemcpy/cudaMemcpy2D；连续行时走 cudaMemcpy 快路径 （cudaMemcpy2D 在 D2H 上会慢 1.8×，这是实现期修正的一个坑）。
  • 行跨距不等于宽度时，按行 memcpy 到连续暂存，保证引擎输入始终连续。

10. 测试与验收设计

10.1 「与 CPU 结果一致」的可执行定义

去畸变在 GPU 上必然存在 FMA 融合顺序差异，追求逐位相等既不现实也无意义。本工程把「一致」 定义为四条硬阈值 + 一条确定性，并在 40 张全量图上逐位置审计：

编号判据阈值理由
A1最大绝对差≤ 1 LSB8 bit 输出的最小可分辨单位；不允许结构性偏差
A2差异像素比例≤ 1×10⁻⁵只允许舍入边界上的孤立像素
A3差 ≥ 2 的像素数= 0排除任何「成片偏色/错位」
A4PSNR（最差图）≥ 60 dB若全图都差 1 LSB，PSNR 约 48 dB； 实测 >99 dB 说明差异极稀疏（<10⁻⁵）
A5重复推理同图 N 次逐位相同排除非确定性（TRT 同 context 应确定）
为什么不用「逐位相等」：CPU 版本自身在启用 FMA 与未启用 FMA 时就有 5.44×10⁻⁶ 的差异 （见 UNDIST-002 §3.2）。把 GPU 的 FMA 差异压到 0 等价于要求 GPU 禁用 FMA， 既不可控也没有工程收益。
