5. pageable vs pinned 内存搬运专章

5.1 机制回顾

GPU · pageable 内存搬运

  • 源/目的是普通可分页内存（new、std::vector、托管数组、cv::Mat）。
  • GPU 的 DMA 引擎不能直接访问可换出页，驱动必须先准备一块页锁中转缓冲： CPU 把数据拷进中转 → DMA 上卡；回读反之。
  • 因此一次 H2D 实际包含「一次额外主机拷贝 + 一次 DMA」，D2H 也一样；同步 API 还要等全程完成。
  • 表现：带宽只有 pinned 的 40–50%，D2H 尾延迟抖动大（本报告 p90 5.62 ms）。

GPU · pinned 内存搬运（工程推荐值）

  • 用 cudaHostAlloc 或 cudaHostRegister 让物理页常驻、不可换出。
  • DMA 直接读写主机物理地址，没有中转拷贝；cudaMemcpyAsync 真正异步。
  • 单帧理论时间 = H2D + kernel + D2H ≈ 0.77 + 1.20 + 0.77 ≈ 2.7–2.9 ms。
  • 代价：不可换出的物理内存；注册/分配毫秒级，必须复用；过量会拖慢整机。

5.3 三个反直觉点（含逻辑分析）

  1. 「库内 pinned 暂存」只比 pageable 快 19%。 4.944 vs 5.904 ms。原因是：把 21 MB 从普通页拷进 pinned 需要约 1.0 ms（读+写各 21 MB）， 一去一回 2.05 ms；这几乎正好等于驱动自己在中转缓冲上多花的钱。 所以「只是把 cudaMemcpy 的源换成 pinned」并不自动变快，关键是数据是否本来就在 pinned 里。
  2. pageable 的 D2H 比 H2D 更贵（2.698 vs 1.913 ms）。 回读要等 GPU 完成、把结果从中转缓冲拷回用户页，WDDM 下还要处理页驻留； 实测 p90 5.62 ms、max 5.94 ms，尾延迟是它不适合实时链路的核心理由。
  3. 零拷贝路径的 kernel 反而略慢（1.354 vs 1.292 ms）。 这是测量顺序/时钟抖动，不是 pinned 影响 kernel；三次独立运行 kernel 区间为 1.03–1.35 ms，与 bench_kernel 的 1.198 ms 一致。看总量时不要把这 5% 当成机制差异。

5.4 C# 侧的关键发现：POH 不是页锁内存

第一版：GC.AllocateArray<byte>(n, pinned:true) + GCHandle(Pinned) → 零拷贝路径 5.929 ms（与 pageable 持平）。
原因：POH/GCHandle 只保证 GC 不移动对象，物理页仍可换出；CUDA 按 pageable 处理。
修正：构造时 cudaHostRegister（导出 undist_host_register）， 析构时 cudaHostUnregister → 2.764 ms（2.15×）。

这条经验对所有「C# + CUDA」封装都成立：托管层的「pinned」与 CUDA 的「pinned」不是同一个概念， 必须显式注册。

6. 与 CPU 版本的一致性分析

6.1 差异来源

来源量级影响
权重重建（fu/fv 乘积 vs A1..A4 查表）≤ 1.19×10⁻⁷对 uint8 量化几乎不可见
GPU FMA 融合（4 项乘加）~1e-7 相对仅 clamp/+0.5 边界附近的像素翻转 1 LSB
CPU 自身 FMA vs mul+add5.44×10⁻⁶（UNDIST-002）与本工程 5.86×10⁻⁶ 同量级

因此「0/40 逐位相同」是预期结果，不代表实现有偏差：把 CPU 自己换一种等价求和顺序， 也会得到同一量级的差异。真正需要守住的是「差 ≥2 = 0」和「差异比例 ≤1e-5」，两项都满足。

10. 结论与建议

验收结论：UndistortionV1 的 TRT 推理结果与 CPU Release 版本在 40 张 5120×4096 全量数据上 满足「最大 ±1 LSB、差异比例 ≤1e-5、无 ≥2 差异、PSNR ≥60 dB、重复确定」五项判据， 验收通过。C ABI 与 C# 封装契约、错误路径、生命周期均通过用例。

10.1 部署建议

  1. 实时链路：用调用方常驻 pinned 缓冲 + 零拷贝，按 2.9 ms/图 设计； 每路相机固定 2 块 20 MiB 页锁缓冲，循环复用。
  2. 已有 Mat 管线：直接用默认 Process(Mat)，按 4.9 ms/图 计价； 不要为「pinned」再包一层临时拷贝，收益接近 0。
  3. 更高吞吐：把去畸变放到 GPU 节点（图不落主机），可到 1.2 ms/图； 多相机/批量场景需要 batch plugin（本版未实现）。
  4. 发布包：引擎随包发布（37 KB），运行时链接 lean 版 TensorRT 可显著减小体积； 注意引擎与 GPU 架构 + TRT 版本绑定。
  5. 启动耗时：2.2 s 主要花在 1 GB 矩阵读取；若不可接受，离线生成 idx0/fu/fv 后只做 H2D（目标 <300 ms）。
