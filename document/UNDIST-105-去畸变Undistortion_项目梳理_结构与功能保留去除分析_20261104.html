1. 结论摘要

项目定位
把 CPU 去畸变算法（undistortion_standaloneV0）做成 TensorRT 推理库： 12 个去畸变矩阵 → 12 B/px 紧凑表 → 20 层原生算子网络，输入输出都是内存图像，不落盘。
交付物
一个原生 DLL（C ABI）+ 一个 .NET 8 类库 + 两个可执行程序（测试 / 工具）。 C++ 侧只是「能力实现层」，C# 侧才是「交付层」。
C# 三个项目
主项目 Undistortion.Inference（类库，Mat 进 Mat 出）、 测试项目 Undistortion.Test（加载指定图像 → 初始化 → 执行 → 释放，85 行）、 工具项目 Undistortion.Tools（批量验收 + 与 CPU 参考图逐像素比对）。
唯一入口
去畸变只保留 Mat 一种方式：Process(Mat) 与 Process(Mat, Mat)。其余入口（byte[] / PinnedBuffer / IntPtr / BenchKernel / SetMemoryMode / QueryLastTiming）已从代码删除，档案见第 5 节。
初始化参数
是一枚 只读结构体 UndistortionConfig（定义在 UndistortionConfig.cs）：矩阵目录、宽、高、设备号、引擎缓存路径。 没有配置文件：没有 JSON、没有加载器、没有路径查找规则；库内零文件 I/O。 离线程序的参数走命令行（矩阵目录显式给，尺寸取首图 Mat.Width/Height）。
日志 / 缓存
日志只服务离线调用：结构体没有日志字段，交付层固定 log_level = 0， C# 上位机不使用也开不了；离线走 C ABI 自己开（见 6.6）。 引擎缓存是可选加速：37 KB，命中 0.15 s、不缓存每次构建 ≈6.7 s（进程 8.51 s vs 1.79 s）。 默认不缓存；参数已从「文件路径」收敛成「目录」，见 6.7。
验收
重构后重新跑了 40 图全量验收：PASS，差异像素 4914 / 838,860,800 = 5.858×10⁻⁶、最大差 1 LSB、差异 ≥2 的像素 0、 PSNR 最小 99.47 dB —— 与重构前 C++ 验收、C# 自测的数值完全一致。
代码量
C# 源码 1222 → 948 行（含注释；纯代码行 566）；类库 701 → 567 行； 公共 API 成员 12 → 6；P/Invoke 声明 10 → 5；三个 csproj 的重复配置收敛到 Directory.Build.props。换掉的是原先混在一起的选项类、配置文件与加载器、 页锁缓冲、比对工具与三种入口；留下的是一个结构体 + 一条 Mat 路径。
一句话：能力层（C++）保持不变，交付层（C#）砍到「config → Mat → Mat」一条线； 被砍掉的四种搬运口径不是丢弃，而是从「可执行代码」变成「可复现文档 + 可观测字段」 （Info.PinnedStaging、LastTiming）。

本节把从代码里删掉的四条旁路入口完整记录下来：原来怎么写、为什么删、实测什么水平、 将来若要恢复怎么恢复。数据全部来自 document/data/acceptance_report.json（原生层，40 图 × 5 次）与 document/data/csharp_selftest.json（旧 C# 自测，3 图 × 3 次）。

5.1 byte[] 入口（Process(byte[]) → byte[]）

原实现

// 旧 API：托管数组进、托管数组出
public byte[] Process(byte[] src)
{
    int expected = Info.Width * Info.Height;
    var dst = new byte[expected];
    GCHandle hSrc = GCHandle.Alloc(src, GCHandleType.Pinned);
    GCHandle hDst = GCHandle.Alloc(dst, GCHandleType.Pinned);
    try   { Process(hSrc.AddrOfPinnedObject(), Info.Width, hDst.AddrOfPinnedObject(), Info.Width, false); }
    finally { hDst.Free(); hSrc.Free(); }
    return dst;
}

为什么去掉

  • 每帧多一次 20 MB 托管数组分配 + 两次 GCHandle 固定，但并不省任何搬运 —— host_flags=false，仍然走库内页锁暂存，耗时与 Mat 路径相同。
  • 接口是「无形状的字节数组」，尺寸/通道全靠长度推断，比 Mat 更容易误用。
  • 旧自测 entry_bytes_equal_mat 证明它与 Mat 入口逐位一致，即纯冗余。

实测

口径单图 total说明
byte[] 入口≈ 5.11 ms与 Mat 路径同属 pinned 暂存口径
Mat 入口4.944 ms差异在噪声内

若要恢复

20 行即可：在 Undistorter 里加一个重载，内部 GCHandle.Alloc + 调用现有的 internal 指针路径。不建议恢复，除非调用方拿不到 Mat。

5.2 零拷贝 PinnedBuffer（工程推荐的高速路径）

原实现

// 旧 API：真正的 CUDA 页锁缓冲（cudaHostRegister），可复用
public sealed class PinnedBuffer : IDisposable
{
    public PinnedBuffer(int length)
    {
        Array    = GC.AllocateArray<byte>(length, pinned: true);   // 只保证地址不被移动
        _handle  = GCHandle.Alloc(Array, GCHandleType.Pinned);
        IntPtr p = _handle.AddrOfPinnedObject();
        int rc   = NativeMethods.undist_host_register(p, length);     // ← cudaHostRegister，关键一步
        ...
    }
    public IntPtr Pointer { get { ... } }
}

// 调用侧
using var pinIn  = new PinnedBuffer(w * h);
using var pinOut = new PinnedBuffer(w * h);
pinIn.CopyFrom(src.Data, pinIn.Length);
und.ProcessPinned(pinIn, pinOut);            // → undist_process(..., host_flags = 1)

为什么去掉

  • 生命周期责任转移：40 MiB 页锁内存（不可换出物理页）要由调用方分配、复用、注销， 一旦忘记 Dispose 就是进程级泄漏。
  • 和 Mat 语义打架：Mat 是「拷进拷出」，零拷贝是「调用方缓冲区直达 DMA」， 一个交付层同时提供两套语义，调用方必然选错。
  • 收益（1.71×）只在「同进程高频连续处理」成立；交付层的主要场景是单图/低频， 且 Mat 路径的 4.944 ms 已满足 202 张/s。

6. 初始化参数：一个 C# 结构体（没有配置文件）

初始化的全部参数 = 一枚只读结构体 UndistortionConfig（4 个字段），定义在 csharp/Undistortion.Inference/UndistortionConfig.cs。 项目里没有配置文件：既没有 JSON，也没有“读配置 / 找配置”的类，库内零文件 I/O。

6.1 为什么是结构体，以及为什么把 JSON 也删了

交付契约用值类型

  • 只有 4 个字段（1 个字符串 + 3 个 int），传参零堆分配；
  • readonly struct + init：构造完不可改，「改尺寸只能重建实例」成为硬约束， 避免运行期被改成半新半旧的配置；
  • 字段与原生 undist_create / undist_options 一一对应，看一眼就知道传了什么；
  • 不绑定文件格式：上位机用自己已有的配置体系填字段即可，库内不做任何文件 I/O。

原来那份 JSON 为什么删

它曾经承担三件事：离线工具的默认参数、相对路径基准、以及 「配置在哪个文件」的查找顺序。

  • 去掉缓存键之后只剩 4 个值（矩阵目录 / 宽 / 高 / 设备号）；
  • 只有我们自己的两个离线程序用，上位机从不用 —— 没有第二个使用方；
  • 这 4 个值脚本本来就知道（run_test.ps1 / run_verify.ps1 的默认参数）， 尺寸还能直接从待处理图像取；
  • 代价不划算：一个文件格式 + 一个加载器 + 相对路径规则 + 4 级查找顺序（≈96 行） 换 4 个数，而且让“配置”出现两个载体 —— 新人第一句就会问「以哪个为准」；
  • 删掉后与仓库里其它工具口径一致：离线参数走命令行（C++ 验收、Python 批处理本来就这样）。

  • 没有控制台：上位机是 GUI 或服务，stderr 要么被丢弃、要么被重定向到文件， 成本不可控，还可能被误当成错误输出采集；

  • 生产不该刷诊断信息：0 档之外的内容属于「开发期信息」，上线后是噪音；
  • 关掉几乎零成本：原生每条日志先做一次 level < need 整数比较就返回， 不做字符串格式化，也不进 IO。

6.7 引擎缓存：交付层为什么固定关闭（重点）

先把代价量出来

同一台机器、同一张图、同一个进程模板，只改「有没有缓存」，量进程总时长：

口径进程总时长其中引擎阶段初始化合计

结论：交付层固定「每次构建」

  • 上位机的形态就是「一次启动、长期运行」：6.7 s 只在进程启动时付一次， 之后每帧 5 ms，占比可忽略；
  • 换来的是一串问题同时消失：路径是否存在、目录是否可写、多实例并发写、缓存与 GPU/TRT 版本不匹配；
  • 还消掉一个隐性黑盒：启动耗时变成恒定的，不需要再解释「这次为什么快 / 慢」；
  • 参数与代码一起变少：结构体 4 个字段，没有路径拼接、没有目录创建、没有写失败分支。

为什么「表」没有缓存

表是 240 MiB（12 B/px × 5120 × 4096）的主机端紧凑表，由 12 个 .bin 现场构建， 耗时 1.3~2.1 s。不做表缓存是刻意的：落盘要 240 MiB、读回也要 240 MiB， 在 NVMe 上并不比直接算快多少，却带来「矩阵换了但缓存没换」的一致性风险。 所以初始化的下限就是这 1.3~2.1 s，引擎缓存只能把 6.7 s 这头压下去。

7.2 约定（写进代码注释，后续照此扩展）

  • 命名空间 = 项目名：Undistortion.Inference、Undistortion.Tools； 不再出现 V1、TRT、CSharp 这类实现细节前缀。
  • 一个公开类型一个文件，文件名 = 类型名（类库 5 个文件对应 5 个类型）。
  • 类名用名词，工具类用 -er（Undistorter、ImageComparer； 数据类用 Info / Timing / Config / Exception）。
  • 私有字段 _camelCase，公开属性 PascalCase，参数 camelCase。
  • 不用可选参数表达「两种语义」：要么两个重载，要么一个明确的方法名。
  • 抛异常带上下文：UndistortionException 一定带原生错误码 + 原生错误串。
  • 文件头注释写清「这个文件负责什么、不负责什么」，避免再次长出旁路能力。
